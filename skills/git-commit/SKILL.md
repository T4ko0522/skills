# Git Commit

コミットメッセージ案や変更の分割相談にも使う。skill を使うこと自体は commit の実行許可ではない。実際の commit と push は、それぞれユーザーが明示的に依頼したときだけ行う。履歴の書き換えには別途明示的な許可が必要で、未依頼のファイルの追加は含まない。

## メッセージ

通常は `type(scope): 日本語の要約`。type は変更の性質から選ぶ（`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`remove`、`deploy`、`revert`）。scope は必要な場合だけ付ける。英語はユーザーが指定した場合だけ使う。

この環境の `prepare-commit-msg` hook は type を対応する gitmoji に置き換える。入力メッセージに絵文字を手で入れない。ログにも type を残す必要があれば先頭に `gm `、絵文字を付けないなら `n ` を付ける。どちらも半角スペースを含むプレフィックスで、hook が最終メッセージから取り除く。

```text
feat(editor): 検索結果を絞り込む       # -> ✨ editor: 検索結果を絞り込む
gm fix(api): タイムアウトを処理する    # -> fix(api): 🐛 タイムアウトを処理する
n chore: 一時的な移行を記録する        # -> chore: 一時的な移行を記録する
```

## 作業方法

1. `git status`、`git diff`、必要なら最近の `git log` で対象と既存の慣行を確認する。
2. ステージ前に、各コミットの目的・対象・依存順序を内部で整理する。コミットが許可済みなら、分割案の提示や追加確認をせず、自律的に分割・検証・コミットする。
3. `git add <対象ファイル>` を使う。同一ファイルを分ける必要がある場合だけ `git add -p` を使う。`git add .` と `git add -A` は使わない。
4. hook を有効にしたまま `git commit` し、`git status` と最終メッセージを確認する。

## コミットの粒度

- 1コミットは、レビュー担当者が一つの目的とその検証を追える単位にする。同じ依頼・機能・移行作業であることを、一括化の理由にしない。
- 依存関係がある変更も、前提となる変更から順に積む。依存更新、機械的な移動、ロジック変更、CI変更などは、意味のある境界と各段階の整合性を確認して分ける。分割数を増やすためだけのファイル別・行数別の分割はしない。
- ロックファイルや生成物は、それを変える元の変更と同じコミットに含める。差分量は生成物と手書きコードを分けて評価し、生成物が大きいことを他の責務までまとめる理由にしない。
- 各コミットは、それ以前のコミットまでで整合し、後続の変更に頼らずビルド・対象の検証ができる状態にする。部分ステージングする場合も、隔離した作業領域などで各コミットの内容に対する対象検証を行う。最終ワークツリーでの成功を、中間コミットの検証結果として扱わない。
- ステージ後に `git diff --cached --stat` と実際の差分を確認する。複数の目的や広い範囲の手書きロジックが残る場合は、コミット前に分割を見直す。

差分を分けるために checkout/reset や編集でユーザーのワークツリーを巻き戻さない。すでに変更が混在している場合は、部分ステージングや隔離した作業領域で再構成する。分割に手間がかかることを一括化の理由にしない。具体的な依存を確認しても整合性のために不可分な変更だけは同じコミットに含め、その理由を本文に記録する。この粒度判断に追加確認は求めない。

## 境界

- `--no-verify` は使わない。
- 機密ファイルや意図不明な untracked file はステージしない。必要なら対象をユーザーに確認する。
- ユーザーが commit だけを依頼した場合は commit 後に止める。`git push` は明示依頼時だけ行う。
