# TypeScript 設計

まず既存の public contract、runtime、依存関係、利用者、変更範囲を確認する。フレームワークや SDK が境界の形を規定するときはその contract に従い、自分が所有する境界だけを設計する。

## 依存関係と互換性

- 標準 API、既存依存、追加依存、自作を、必要な機能、運用責任、対応 runtime、導入コストで比べる。新しい API や依存更新が判断を左右するときは、対象バージョンの公式資料を確認する。
- 互換性、移行、破壊的変更は、公開範囲、利用者、データの寿命、変更の便益から決める。必要な移行は明示し、理由のない互換レイヤーと理由のない破壊的変更の両方を避ける。

## 責務と抽象化

- I/O、ネットワーク、永続化、ログのような効果と、純粋な変換・方針決定を分ける。ただし層、interface、DI を増やすのは、独立した責務、複数の実装、または交換可能な境界を表す必要があるときに限る。
- 関数・モジュール・component の境界は、呼び出し側が知るべき contract、状態の所有者、変更理由、再利用の見込みで決める。小ささ、行数、使用箇所数、重複だけを根拠に分割・統合しない。
- 見た目が似ていても失敗方針、寿命、所有する状態が異なる処理は分ける。逆に同じ知識と方針を保つための共通化は有効である。
- closure、class、関数、オブジェクトは、public API、ライフサイクル、共有状態、既存規約の読みやすさで選ぶ。可変状態は所有者と寿命を局所化し、更新規則を読み取れるようにする。

## 型と境界

- 型は実行時の検証を置き換えない。HTTP、環境変数、設定、CLI、ファイル、外部 SDK の値は、信頼境界で runtime validation または狭い type guard に通し、下流には検証済みの contract を渡す。
- 検証・パース・正規化などの汎用的な処理は、標準 API や適切なライブラリに責務を委ね、同等のロジックを自作しない。アプリケーション側では、スキーマや設定による制約の定義と、ドメイン固有のルールを担う。
- 推論で十分な実装内部では型を重複させない。公開 API、再帰、複雑な generic、意図した contract を固定する場面では、明示的な型が読みやすさと変更検出を助ける。
- 判別 union、literal union、schema 由来の型、exhaustive handling は、追加された variant や不正な状態を型で検出できるときに使う。既存の公開型や宣言マージの必要性に合わせて `type` と `interface` を選ぶ。

## エラーと非同期

- 失敗を exception、Result、判別された値、イベントのどれで表すかは、呼び出し側がいつ・誰が回復を判断するかで決める。失敗の文脈と原因を失わず、境界で観測・報告できるようにする。
- callback、Promise、EventEmitter、stream は、通知回数、購読者、順序、backpressure、runtime の慣習に合わせて選ぶ。事実の発行と、その失敗をどう扱うかの方針を分ける。
- Promise の所有者と完了時の扱いを明確にする。並行処理では取消、timeout、retry、部分失敗、解放順序を要求に応じて設計し、取得した資源にはその場で解放経路を対応付ける。

## 検証

- テストは public seam、重要な分岐、失敗モード、統合境界を、変更リスクに見合う粒度で確認する。純粋な変換、配線、外部サービスのどこを unit・integration・e2e で確かめるかは、観測したい振る舞いと実行コストで選ぶ。
- UI コンポーネントの振る舞いは、重要なユーザーフローの E2E テストで確認し、コンポーネント単位の unit・integration テストは原則追加しない。UI から独立した業務ルールや状態遷移は unit test の対象とする。ただし、テストのためだけに UI の内部処理を分離・公開しない。
- テスト可能性は設計判断の一つだが、テストの都合だけで product contract を歪めない。必要な test double は、所有していない境界または高コストな依存を表し、実際の統合確認で補う。
